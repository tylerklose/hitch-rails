# Upgrading hitch-rails 0.2 → 0.3

This upgrade adds refresh tokens. It requires **one new migration** and no
configuration changes. Written to be executed directly, by a person or by an
agent working in the host application.

## What you are changing, in one paragraph

In 0.2 an MCP client's access token lasted an hour and there was no way to
renew it, so a connector's only recovery was sending its human back through
the OAuth consent screen. 0.3 issues a refresh token beside the access token
and accepts `grant_type=refresh_token`, so the client renews itself in the
background. Refresh tokens rotate on every use and a replayed one revokes the
whole grant family. The feature is **on by default**.

## Before you start

Confirm you are actually on 0.2.x and that the working tree is clean:

```bash
bundle list | grep hitch-rails     # expect 0.2.x
git status --porcelain             # expect empty
```

If the app is already on 0.3.x, stop — this guide does not apply.

## Step 1 — point at 0.3

**If 0.3.0 is published on RubyGems:**

```ruby
# Gemfile
gem "hitch-rails", "~> 0.3.0"
```

**If you are tracking `main` ahead of the release** (the expected path while
0.3.0 is being dogfooded):

```ruby
# Gemfile
gem "hitch-rails", github: "tylerklose/hitch-rails", branch: "main"
```

Pin to a SHA instead of `branch:` if you want a reproducible build. Then:

```bash
bundle install
```

## Step 2 — run the migration

Hitch appends its migrations to your app's migration paths, so there is
nothing to copy or generate:

```bash
bin/rails db:migrate
```

This applies `20260822000000_add_hitch_refresh_tokens`, which adds five
columns and two indexes to `hitch_access_tokens`. It is additive — no existing
column or index is altered, and the 0.2 migration is untouched.

**Do not skip this step.** Refresh-token issuance is on by default and writes
columns the migration adds, so on an unmigrated database the *authorization
code exchange* fails — not just refresh. That breaks the whole OAuth flow.
Rails raises `ActiveRecord::PendingMigrationError` in development and test,
and `bin/rails hitch:doctor` reports it, but a production deploy that skips
migrations will fail at runtime.

## Step 3 — verify

```bash
bin/rails hitch:doctor
```

Expect `migrations` to report `current`. If it reports `missing`, step 2 did
not run.

Then confirm the grant is actually being advertised and honored:

```bash
# Discovery should now list refresh_token
curl -s https://your-app.example.com/.well-known/oauth-authorization-server \
  | grep -o '"grant_types_supported":\[[^]]*\]'
# expect: "grant_types_supported":["authorization_code","refresh_token"]
```

If you have an integration test that completes a code exchange, assert the
response now carries a `refresh_token` key. Hitch's own suite does this in
`test/integration/refresh_token_flow_test.rb` if you want a model.

## What might break in your app

None of this is a required change, but check each:

1. **Tests asserting the exact shape of the token response.** Successful
   `/oauth/token` responses now include a `refresh_token` key. An assertion
   like `assert_equal %w[access_token token_type expires_in scope], body.keys`
   will fail. Loosen it or add the key.
2. **Tests asserting `grant_types_supported`.** It is now
   `["authorization_code", "refresh_token"]` rather than a single entry.
3. **A snapshot or contract test over discovery metadata.** Same reason.
4. **Anything that scheduled `Hitch::AccessToken.cleanup_expired!` and
   asserted a row count.** Cleanup now keeps two classes of row past the
   retention window (see below), so counts will differ.

Nothing else in the 0.2 surface changed. No method was removed or renamed.

## Decisions you may want to make

Both are optional, and the defaults are deliberate. **If you are an agent
performing this upgrade, do not change either without asking the human first**
— they are security posture, not configuration cleanup.

### Should refresh tokens be on?

They are on by default. This is the only setting in the gem whose library
fallback is `true`, because the flag guards *exposure*, not whether the
feature does its job — a flag nobody flips leaves every connector nagging
hourly. Turn it off only if a threat model calls for it:

```ruby
config.refresh_tokens_enabled = false
```

That also drops `refresh_token` from `grant_types_supported`, so clients stop
being told about a door that is shut.

### Should a grant have a hard cutoff?

By default a grant continues as long as it keeps being used; one that stops
being used lapses after the idle window (30 days). There is no absolute
ceiling.

The residual risk of that, stated plainly: rotation and reuse detection catch
a thief the moment the legitimate client refreshes again, because the replay
collides with a consumed token and the family dies. They cannot catch a theft
where the legitimate client *never comes back* — nothing collides, so nothing
trips the alarm, and the stolen token keeps working until someone revokes it
through `/oauth/revoke`. If that case matters to you:

```ruby
config.refresh_token_family_lifetime_seconds = 90 * 86_400
```

Every family started after that carries the ceiling. Note the cost: a ceiling
does not reset, so it disconnects people who have done nothing wrong — daily
users included — the moment it passes.

## Operational notes

`cleanup_expired!` now keeps two things past `revoked_retention_days`: a row
still holding a usable refresh token, and a consumed row recent enough to be
reuse-detection evidence. Both are deferrals, not exemptions — rows are
collected once the refresh token has expired and the evidence is older than
the window. Expect a modestly larger `hitch_access_tokens` table, roughly one
retention window's worth of rows per actively-refreshing connector.

If that matters at your scale, lower `revoked_retention_days` or set a family
ceiling.

## Rolling back

```bash
bin/rails db:rollback     # drops the five columns and two indexes
```

Then restore the 0.2 constraint in your `Gemfile` and `bundle install`.

Any refresh tokens already issued stop working, which clients handle by
falling back to the full OAuth redirect — the 0.2 behaviour. Access tokens are
unaffected and keep working until they expire normally. No data an adopter
owns is lost; the dropped columns hold only Hitch's own token state.
