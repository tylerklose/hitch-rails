# Adopting the internal Hitch 0.1.0 checkpoint

`0.1.0` itself was never published. These steps are for approved applications
that pin the accepted checkpoint's full source commit while the auth substrate
and 0.2 framework are being built.

## Before changing code

1. Back up the Hitch tables and record the deployed commit.
2. Confirm the application uses Ruby `>= 3.3, < 4.1`, Rails `>= 7.2, < 8.2`,
   and SQLite or PostgreSQL.
3. Drain every old process or job that can create clients or mutate redirect
   URIs. Keep DCR and operator client writes disabled through redirect cutover.
4. Set the canonical external MCP resource in `config.resource_uri`. Hitch's
   issuer is now the exact origin of this URI; request `Host`, `Forwarded`, and
   `X-Forwarded-*` values do not change discovery.

`config.allowed_hosts` now means additional exact ingress aliases only. Remove
schemes, ports, paths, wildcards, and any entry used solely to influence issuer
generation. Set exact browser origins in `config.allowed_origins`.

## Choose registration posture explicitly

Set both registration choices deliberately:

```ruby
config.client_id_metadata_enabled = true
config.dynamic_client_registration_enabled = false
```

Before enabling CIMD, run:

```sh
bin/rails 'hitch:cimd:check[https://a-client-you-trust.example/client.json]'
```

CIMD requires direct outbound HTTPS egress and does not use proxy environment
variables. If DCR must remain enabled in production, configure a fleet-shared
atomic rate store as described in the public API manifest. DCR is now
JSON-only, rejects duplicate JSON names, caps bodies at 16 KiB, and applies the
documented client/redirect bounds. A client relying on form registration,
duplicate-key last-wins parsing, empty redirects, duplicate redirects, or more
than 32 redirect URIs must be corrected before the upgrade.

## Migrate and cut over redirects

Deploy the new code with old redirect writers still drained, then run:

```sh
bin/rails db:migrate
bin/rails hitch:redirects:cutover
```

The migrations add normalized `hitch_client_redirect_uris`, credential
columns, delete cascades, and lossless string storage for polymorphic
`principal_id`. Integer IDs retain their text value; UUID and ULID principal
IDs now round-trip on SQLite and PostgreSQL.

`hitch:redirects:cutover` copies legacy redirects, proves parity, and changes
the authority marker atomically. Do not return old writers to service after
that marker changes. Start only the new application version and verify OAuth
with an existing client before restoring normal traffic.

Legacy redirect rows containing more than the new-write bounds are copied
losslessly during cutover. The finite limits apply to new registrations and
mutations; migration does not silently truncate old authority.

## Rollback during source adoption

Before rolling application code back, drain every redirect writer again and
run:

```sh
bin/rails hitch:redirects:prepare_rollback
```

The task refuses to change authority when representations disagree. Only after
it reports legacy authority may the old code return to service.

The principal-ID migration intentionally refuses a destructive database
rollback once a nonnumeric ID exists. Keep the widened string column and roll
application code forward instead; coercing UUID/ULID authority to an integer
would bind tokens to the wrong principal or lose the binding entirely.

## Verify

Run the host's tests plus an exact live discovery/authorization example. Check
that discovery uses the configured canonical issuer even through ingress
aliases, unsupported scopes are not granted, existing redirect URIs resolve
from normalized rows, and one exchanged authorization code cannot be replayed.

The complete internal 0.1 checkpoint contract is in
[`docs/public_api/0.1.0.md`](../public_api/0.1.0.md).
