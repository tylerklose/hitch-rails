# Upgrading hitch-rails 0.4 → 0.5

0.5 adds Rails 7.2 support and opt-in untrusted-text labeling, fixes registry
boot and reload timing, and tightens native redirect and Client ID Metadata
Document (CIMD) validation. **There are no new migrations from 0.4.** Existing
feature switches keep their defaults; review custom native clients and CIMD
servers before deploying.

## Update the dependencies

For an application on 0.4.x:

```ruby
# Gemfile
gem "hitch-rails", "~> 0.5.0"
```

```sh
bundle update hitch-rails mcp
```

Hitch now requires `mcp >= 1.4, < 2`, so update any host constraint that
pins the SDK below 1.4. Ruby remains >= 3.3, < 4.1. Rails now accepts >= 7.2,
< 9; this adds a supported Rails 7.2/Rack 2.2/PostgreSQL lane alongside Rails
8.0/SQLite and Rails 8.1/PostgreSQL. An existing Rails 8 application does not
need to change Rails or its database adapter.

Do not copy engine migrations or rerun the install generator. If upgrading
from an older release, apply its upgrade guide first; 0.4's migrations are
still required.

## Review native OAuth clients

0.4 accepted arbitrary hierarchical custom redirect schemes. 0.5 accepts
HTTPS, loopback HTTP, and explicitly allowlisted native schemes, following
[RFC 8252 §7](https://www.rfc-editor.org/rfc/rfc8252#section-7). Native
redirects also require a trusted source for that client:

- `grokbot` is shipped with CIMD vouchers for `grok.com`, `x.ai`, and one
  subdomain of `x.ai`.
- `cursor` is shipped with CIMD vouchers for `cursor.com`, `cursor.sh`, and
  one subdomain of either.
- An operator-registered **confidential** client may use an allowlisted
  native scheme without a CIMD voucher. Ordinary public registrations and
  self-registered DCR clients do not qualify.

For your own scheme and metadata host, add both settings in the existing
Hitch initializer:

```ruby
config.native_redirect_schemes = [ "com.example.agent" ]
config.native_redirect_vouchers = {
  "com.example.agent" => "agent.example.com"
}
```

The voucher is the host serving the client's CIMD document, not the host
component in its native redirect URI. Assignment preserves the shipped
schemes and vouchers. Omitting a voucher makes an added scheme available
only to operator-registered confidential clients. Privileged schemes such as
`javascript`, `file`, `intent`, `chrome-extension`, and `web+*` remain refused.

This policy is checked at authorization time, including for redirect URIs
already stored in the database. A previously registered custom-scheme client
may therefore stop authorizing until its scheme and provenance satisfy the
policy. Open DCR cannot register native redirects; use a vouched CIMD client,
an operator-registered confidential client that supports Basic client
authentication, or an HTTPS/loopback callback instead. Adding only the scheme
does not authorize an existing public DCR client. PKCE S256 remains required.

If you customize consent views or client labels, preserve the new identity
source: native redirects display the CIMD document host or the
operator-registered client's scheme. The native URI's host is not a verified
client identity.

## Check CIMD documents you depend on

When CIMD is enabled, 0.5 refuses:

- Metadata URLs with trailing-dot hosts or `.` / `..` path segments.
- Successful responses whose Content-Type is neither `application/json`
  nor `application/*+json`.
- Documents with any redirect URI longer than 255 bytes.

The document's `client_id` must still match its fetch URL exactly. URL
validation follows
[draft-ietf-oauth-client-id-metadata-document-02 §3](https://www.ietf.org/archive/id/draft-ietf-oauth-client-id-metadata-document-02.html#section-3).
Fix the serving endpoint or client configuration if it relied on an accepted
0.4 shape. The diagnostic fetches a document through the current checks:

```sh
bin/rails 'hitch:cimd:check[https://agent.example.com/client.json]'
```

A TLS, connection, or HTTP failure now suppresses only the failing URL;
DNS failures and blocked addresses can still suppress the whole host. No
cache migration is required.

## Verify the host integration

```sh
bin/rails hitch:doctor
bin/rails test
```

Also verify your application's production-style eager boot and one real MCP
tool call. Eager applications build the registry after Rails eager loading;
non-eager applications build it on first MCP use. Reload clears the old
snapshot before unloading classes. Hosts do not need manual registry
preparation hooks; remove workarounds added solely for Hitch's early
`to_prepare` warning and check the ordinary boot/request path.

Authorization-code failures now share one public `invalid_grant`
`error_description`; adjust tests that distinguished wrong client, redirect,
PKCE, expiry, or unknown code by that text. Device activation pages now send
`Cache-Control: no-store` and `Referrer-Policy: no-referrer`.

`Hitch::MCP::UntrustedText.wrap(text, source:)` is optional. Existing tool
results are not wrapped automatically. The MCP endpoint remains stateless;
updating the SDK does not enable `subscriptions/listen` or streaming.
The identity assertion ADR remains a proposal and adds no grant to 0.5.

## Rollback

Restore the prior Gemfile and lockfile and deploy the previous application
build. There is no 0.5 migration to reverse. A rollback also restores the
older redirect and metadata validation, so it restores those security gaps.
