# Work packet: M1.0

## Scope

Convert the remaining roadmap graph into complete, dependency-checked build
packets before 0.2 runtime implementation begins. Create one packet for every
issue from M1.1 through M8 using the same required section schema as H0's M0
packets. Each packet must name exact files/public or private APIs, exclusions,
predecessors, executable acceptance commands, issue-owned evidence paths,
rollback class/procedure, estimate, concrete risks, and accountable owner.

Extend `bin/verify-work-packets` to validate known issue identifiers,
dependencies, missing/duplicate nodes, cycles, required sections, nonempty
bodies, unresolved placeholders, command ownership, and evidence-path ownership.
Generate a canonical dependency graph from packet metadata and compare it with
the ROADMAP issue table. No implementation issue may start until its packet and
all predecessors pass verification.

## Not in scope

- Implementing M1.1 or any MCP runtime/generator/adoption behavior.
- Reopening fixed release-profile decisions merely to fill a packet.
- Granting access to private adoption hosts or approving paid/model-backed
  smokes; those remain Tyler-owned gates.
- Replacing ROADMAP as the product/milestone authority.

## Target files/API

- `docs/work_packets/M1.1.md`, `M1.2.md`, `M1.3.md`, `M2.1.md`, `M2.2.md`,
  `M2.3.md`, `M3.1.md`, `M3.2.md`, `M3.3.md`, `M4.1.md`, `M4.2.md`, `M4.3.md`,

  `M7.md`, and `M8.md` (new): complete later-work packets.
- `bin/verify-work-packets`: add dependency/ownership checks and deterministic
  graph output while preserving H0's section validation and explicit-file mode.
- `docs/work_packets/schema.md` (new): document machine-readable metadata and
  human section rules used by the verifier.
- `test/tooling/verify_work_packets_test.rb` (new): isolated fixtures for
  missing sections/nodes, cycles, unknown dependencies, unowned commands/evidence
  paths, placeholder text, and stable graph output.

The verifier is contributor tooling, not gem runtime API. Packet contents govern
implementation scope but do not become shipped public API until their milestone
manifest says so.

## Dependencies

- M0.5 and the internal `0.1.0` checkpoint are accepted, with H0/M0 packets
  retained as verified history. Public distribution remains deferred.
- ROADMAP's issue table and fixed profile are the source for required nodes and
  dependencies. This issue creates all new packets, tooling tests, schema docs,
  and evidence paths it names.

## Acceptance commands

Run:

```sh
bin/verify-work-packets
bin/verify-work-packets --graph \
  docs/evidence/0.2.0/contract/work-packet-graph.json
bin/ci-test test/tooling/verify_work_packets_test.rb
bin/rubocop
```

This issue adds the `--graph` option and test file before invoking them. The
default command must validate every packet, find exactly the roadmap issue set,
and exit nonzero for any missing section/node, cycle, unknown predecessor,
unowned command/evidence path, or unresolved placeholder. Two graph runs must be
byte-identical.

## Evidence paths

Create `docs/evidence/0.2.0/contract/work-packet-graph.json` as canonical
verifier output and `docs/evidence/0.2.0/contract/work-packet-verification.json`
with command versions, packet count, edge count, graph checksum, and test
outcome. Do not embed private repository URLs, credentials, or deployment data;
M6/M7 packets name authority and required provenance without secrets.

## Rollback

R1: revert packet/tooling changes together. No runtime or schema state changes.
If any later issue has started, stop it before reverting M1.0 because its scope
and acceptance authority would otherwise disappear.

## Estimate

One engineering day with product/release-maintainer review. Risk is medium:
there is no runtime mutation, but incomplete packets transfer hidden decisions
and can create expensive downstream rework.

## Risks

- A schema-only verifier can pass packets whose commands or evidence directories
  are impossible until a later issue.
- The prose graph and machine graph can drift unless the verifier compares both.
- Private-host milestones can expose sensitive URLs or imply authority the
  contributor does not have; packets must name the owner/gate without secrets.
- Oversized packets hide parallel work and rollback boundaries; split any issue
  that cannot retain one owner, estimate, and rollback procedure.
