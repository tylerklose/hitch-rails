# Work packet: M4.3

## Scope

Implement authenticated endpoint-wide fixed-window admission with one Redis Lua
increment/first-expiry script. Derive keys as HMACs over the validated principal
type/id and client ID, share quota across discover/list/call, return conservative
429 `Retry-After`, fail closed with 503 on store errors, and provide a private
memory store only for development/test.

## Not in scope

- Per-tool quotas, distributed concurrency leases, unauthenticated DCR limits,
  business capacity controls, or alternate production stores.
- Raw principal/client identifiers in Redis keys.

## Target files/API

- MCP configuration readers for request limit and Redis URL.
- private `Hitch::MCP::RedisRateStore`, memory store, HMAC key derivation, and
  Lua script.
- cross-process SQLite/PostgreSQL admission tests and `bin/ci-rate-limit` (new).

Only configuration behavior is public; stores/keys/scripts are private.

## Dependencies

M4.1 is accepted. The pinned Redis image/digest and redis gem range remain the
M1.3/M0 contract.

## Acceptance commands

Run:

```sh
bin/ci-rate-limit
bin/ci-appraisal rails_7_2_sqlite
bin/ci-appraisal rails_8_1_postgresql
```

Prove Lua atomicity/first expiry, token-rotation stability, principal/client
separation, process sharing, exact limit boundary, 429/503 zero downstream work,
and production refusal without Redis.

## Evidence paths

Create `docs/evidence/0.2.0/rate-limit/cross-process.json` with image digest,
process counts, synthetic key digests, timing bounds, and store-error outcomes.

## Rollback

R1 before M4 internal-candidate acceptance. If production traffic exists,
disable or route away from the MCP endpoint before removing the required
admission store.

## Estimate

Four engineering days. Risk is high because race/error behavior is fleet-wide.

## Risks

- Split increment/expiry can create immortal keys.
- Token-based keys let rotation reset quota.
- Redis errors treated as allow bypass admission.
- Clock/window boundary tests can flake without controlled time.

## Owner

The Hitch release maintainer owns rate/store acceptance; operators own Redis
capacity and availability.
