# hitch-rails 0.2 development API

This file tracks the intended `0.2.0` compatibility surface while the internal
prereleases are built. The current development identity is `0.2.0.pre.2.dev`;
the latest sealed internal checkpoint is `0.2.0.pre.1`.
There is no public RubyGems release, and unfinished milestone contracts are not
callable merely because they appear in the roadmap or contract manifests.

The accepted internal `0.1.0` checkpoint remains documented separately in
[`0.1.0.md`](0.1.0.md). Its OAuth, discovery, installation, and deprecated
`Hitch::ServerEndpoint` contracts continue through the 0.2 line unless this
document explicitly narrows them.

## Implemented development surface

`Hitch::Configuration#mcp` returns the one persistent
`Hitch::MCP::Configuration` object owned by the top-level Hitch configuration.
M2.2 adds two settings:

- `server_info=` accepts a callable invoked once per admitted request. It must
  return a Hash with nonempty String `name` and `version`, plus optional
  String `title` and `instructions`. Missing, raising, or malformed values
  produce a generic protocol internal error without registry or SDK work.
- `max_request_bytes=` accepts a positive Integer and defaults to 1 MiB. The
  current value is read for every request; overflow returns 413 before JSON
  parsing.

The callable receives a fresh public `Hitch::MCP::Context` for every admitted
request. It is a frozen envelope with readers for `principal`, `access_token`,
`scope`, `granted_scopes`, `client_id`, `resource`, `request_id`, `remote_ip`,
`user_agent`, `protocol_version`, and `meta`. Principal, token, and scope are
opaque request-local references rather than objects Hitch claims to freeze.
All scalar request values, granted scopes, and untrusted metadata are copied;
metadata is recursively frozen. Client metadata never supplies authority.

`config.mcp.registry=` accepts one nonempty String constant name. The named
constant must resolve to a `Hitch::MCP::Registry` subclass, whose only admission
path is `register ToolClass, scopes: [...]`. Registration stores the tool class
name and copied static scopes, never the reloadable class object. A Rails
`to_prepare` callback clears the prior snapshot, reconstantizes and validates
the entire registry, and publishes one immutable MCP-name-sorted replacement.
Failure raises and leaves the registry unavailable rather than serving a stale
or partial snapshot.

During this staged development line, an auth-only 0.1 adopter with neither MCP
runtime setting continues to boot unchanged. Setting `config.mcp.server_info`
activates the new endpoint runtime and therefore makes `config.mcp.registry`
mandatory at boot; setting only a registry also schedules prepare validation.

Registered classes subclass `Hitch::MCP::Tool` and declare `tool_name`,
`description`, `input_schema`, optional `output_schema`, and optional
`annotations`. Names use 1–64 ASCII letters, digits, underscores, dots, or
dashes. Schemas are JSON Schema 2020-12 objects with same-document references
only and fixed limits of 64 levels, 10,000 schema objects, and 1 MiB serialized
bytes. An effective explicit top-level `server_context` property is reserved;
nested and pattern-admitted values remain schema data but are rejected if
actually supplied at the verified call boundary. Tool annotations accept only
`title` and the four MCP Boolean hint fields. Registry validation also rejects
unsupported or duplicate scopes, duplicate MCP names, unnamed/missing/non-tool
classes, and any subclass replacement of framework-owned `.call`.

`Hitch::MCP::Endpoint` is a public concern for a dedicated
`ActionController::API` controller:

```ruby
class McpController < ActionController::API
  include Hitch::MCP::Endpoint
end
```

The host owns a catch-all route placed before the root engine mount:

```ruby
match "/mcp", to: "mcp#handle", via: :all
mount Hitch::Engine => "/"
```

The concern owns stateless final-profile POST and OPTIONS handling. Its fixed
order is raw Host, exact Origin, method, bearer authentication with active
canonical audience and client binding, then a private admission seam. It
requires the request path/query to equal the canonical resource, validates
Content-Type and both required Accept media types, reads at most the configured
byte cap, rejects duplicate JSON members at any depth, validates modern request
metadata and MCP headers, and dispatches one frozen request through one fresh
SDK server. Forwarded headers never derive the challenge or server identity.

This M2.2 slice exposes exactly one private read-only wire tool,
`hitch.echo`. It exists only to prove authenticated discovery/list/call through
the packaged endpoint and is not an adopter extension point or compatibility
promise. M3 replaces it with the host-owned Registry. Production Redis request
limiting and public request/invocation events remain M4 work. M3.2 has made the
Registry declaration and prepare-time validation APIs callable, but M3.3 still
owns per-principal resolution and replacing this private wire tool. M2.2 uses private
forced seams only to preserve and verify callback precedence.

The installer remains unchanged until M5, so this development controller,
route, and MCP configuration are manual.

The gem directly depends on `mcp >= 1.1, < 2` and
`json_schemer >= 2.4, < 3`. Hitch's SDK adapter, verified
request, staged tool, and version-scoped response normalizer are private
implementation details, not public constants or extension points. Context is
the public exception; its construction remains framework-owned.

`tools/call.params.arguments` may be omitted, as allowed by the protocol. When
present it must be an object. Unsupported protocol versions keep Hitch's frozen
`error.data.supportedVersions` field and additionally expose the official
runner's `supported` list plus the echoed `requested` value.

The M2.3 acceptance harness is test infrastructure, not runtime API. Its five
fixture tools, separate runner-only missing-capability diagnostic, private
bearer-file bridge, npm lock, and checked patch are never packaged. The gate
runs only `server-stateless`, `http-header-validation`,
`dns-rebinding-protection`, `json-schema-2020-12`, `tools-list`,
`tools-call-simple-text`, and `tools-call-error`. It does not claim prompts,
resources, caching, subscriptions, or all-server-suite conformance.

## Distribution status

All `0.2.0.pre.1` through `0.2.0.pre.3` artifacts are internal checkpoints.
`0.2.0.pre.4` is the first public-eligible prerelease, but publication may be
deferred so that final `0.2.0` becomes the first public RubyGems release. Every
tag, GitHub release, or RubyGems publication requires an explicit maintainer
decision after its milestone gates pass.
