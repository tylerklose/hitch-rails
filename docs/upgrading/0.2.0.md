# Adopting the internal Hitch 0.2 framework

No 0.2 artifact has been published. These steps are for an approved source
adopter moving from Hitch's internal auth-only checkpoint or a host-owned MCP
endpoint to an accepted 0.2 commit pinned by its full SHA.

## Before changing the canonical route

1. Back up every `hitch_*` table and record the deployed application and Hitch
   commits.
2. Complete the [0.1 adoption and redirect cutover](0.1.0.md). Version 2 must
   be the normalized redirect authority before the final 0.2 route switch.
3. Inventory the old MCP controller, tool names and schemas, OAuth scopes,
   argument policy, audit meaning, and clients. A framework migration must not
   silently broaden any of them.
4. Provision fleet-shared Redis and inject `HITCH_MCP_REDIS_URL` in every
   production process. Follow the [Redis operator guide](../operator/redis.md).

## Install the host-owned runtime

Run the generators only after the auth initializer and migrations are present:

```sh
bin/rails generate hitch:mcp:install
bin/rails generate hitch:tool echo
```

Both generators refuse collisions before writing. If the existing canonical
controller or `/mcp` route collides, keep it in place while preparing a
namespaced controller or an isolated preview; do not overwrite it. The MCP
installer supports `--controller-name Admin::McpController` but still owns the
one canonical route block it creates.

Implement the generated Tool schema, conservative annotations, request-local
availability, argument authorization, and Result return. Then add the printed
registration line to `McpToolRegistry` manually. The generator never registers
a tool and generated policy denies until the host changes it deliberately.

## Verify before cutover

In an isolated environment, verify OAuth discovery and token exchange, then
use `Hitch::MCP::TestHelper` to discover, list, and call with real host policy.
Run:

```sh
bin/rails hitch:doctor
HITCH_DOCTOR_FORMAT=json bin/rails hitch:doctor
```

Every doctor failure blocks cutover. Review warnings: an empty Registry means
no tool is exposed; the memory store is supported only outside production; a
noncanonical deprecated endpoint is acceptable only during a staged migration.

Replace the canonical route atomically only after the preview proves the same
or narrower tool visibility, scopes, and argument behavior. Keep the old route
change revertible until exact client smokes pass.

## Rollback

Route rollback is a host deployment operation. Restore the previous canonical
route first if the new endpoint is unhealthy. While the gem remains installed,
remove each manually added Registry line and use the matching
`bin/rails destroy hitch:tool ...` only for byte-identical generated files.
Then use `bin/rails destroy hitch:mcp:install` only if its controller,
initializer, Registry, manifest, and marked route block remain unchanged.

Any checksum or route mismatch refuses deletion. Review customized host code
manually; never bypass the refusal with recursive deletion. Do not drop Hitch
tables as part of application rollback. Follow the [removal guide](../removing.md)
for long-term data retention and uninstall decisions.
