# Work packet: M4.3

## Scope

Implement authenticated endpoint-wide fixed-window admission through the host
application's own `ActiveSupport::Cache` store, exactly as
`ActionController::RateLimiting` does. Derive keys as HMACs over the validated
principal type/id and client ID, share quota across discover/list/call, return
conservative 429 `Retry-After`, and fail closed with 503 on store errors.

Hitch declares no Redis dependency and adds no service to a deployment. Redis,
Solid Cache, and Memcached are equally supported backends; the host chooses.

## Not in scope

- Per-tool quotas, distributed concurrency leases, unauthenticated DCR limits,
  or business capacity controls.
- A Hitch-owned store abstraction, connection lifecycle, or Lua script.
- Raw principal/client identifiers in store keys.

## Target files/API

- MCP configuration readers for request limit and `rate_limit_store`, plus the
  production store-capability check.
- HMAC key derivation in private `Hitch::MCP::RateLimitKey`.
- the admission callback in `Hitch::MCP::Endpoint`.
- cross-process SQLite/PostgreSQL admission tests and `bin/ci-rate-limit`.

Only configuration behavior is public; keys and the admission callback are
private.

## Dependencies

M4.1 is accepted. The pinned Redis image/digest remains the M1.3/M0 contract for
the cross-process lane, which exercises `RedisCacheStore` as one supported
backend rather than as a required service.

## Acceptance commands

Run:

```sh
bin/ci-rate-limit
bin/ci-appraisal rails_7_2_sqlite
bin/ci-appraisal rails_8_1_postgresql
```

Prove first-write expiry, token-rotation stability, principal/client separation,
process sharing, exact limit boundary, 429/503 zero downstream work, that a
Solid Cache application boots in production without Redis, and that production
refuses a store which cannot count across processes.

## Evidence paths

Create `docs/evidence/0.2.0/rate-limit/cross-process.json` with image digest,
process counts, synthetic key digests, timing bounds, resolved store class, and
store-error outcomes.

## Rollback

R1 before M4 internal-candidate acceptance. If production traffic exists,
disable or route away from the MCP endpoint before changing the admission store.

## Estimate

Four engineering days. Risk is high because race/error behavior is fleet-wide.

## Risks

- A store that rewrites expiry per increment turns the fixed window into a
  sliding one that never resets under sustained load.
- Token-based keys let rotation reset quota.
- Store errors treated as allow bypass admission.
- A cache store may evict a live counter, which fails open; hosts needing a hard
  control configure a dedicated store.
- Clock/window boundary tests can flake without controlled time.

## Owner

The Hitch release maintainer owns admission acceptance; operators own the
capacity and availability of whichever cache store they configure.
