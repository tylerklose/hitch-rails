# Upgrading hitch-rails 0.3 → 0.4

This upgrade adds the OAuth 2.0 Device Authorization Grant (RFC 8628). It
requires **three new migrations** and no configuration changes — the feature is
**off by default**. Written to be executed directly, by a person or by an
agent working in the host application.

## What you are changing, in one paragraph

In 0.3 a headless agent — a cron job, a `claude -p` invocation, a script on
a box with no browser — could only get a token by having an operator SSH in
and run `hitch:tokens:issue`. 0.4 adds the flow your TV uses: the agent asks
`POST /oauth/device_authorization` for a short code like `WDJB-MJHT`, its
human opens `/activate` on any device, signs in the way your app always
signs them in, approves on a consent screen, and the polling agent receives
an ordinary token. Nothing changes until you enable it.

## Before you start

Confirm you are actually on 0.3.x and that the working tree is clean:

```bash
bundle list | grep hitch-rails     # expect 0.3.x
git status --porcelain             # expect empty
```

If the app is already on 0.4.x, stop — this guide does not apply.

## Step 1 — point at 0.4

**If 0.4.0 is published on RubyGems:**

```ruby
# Gemfile
gem "hitch-rails", "~> 0.4.0"
```

**If you are tracking `main` ahead of the release:**

```ruby
# Gemfile
gem "hitch-rails", github: "tylerklose/hitch-rails", branch: "main"
```

Pin to a SHA instead of `branch:` if you want a reproducible build. Then:

```bash
bundle install
```

## Step 2 — run the migration

Hitch appends its migrations to your app's migration paths, so there is
nothing to copy or generate:

```bash
bin/rails db:migrate
```

This applies `20260824000000_create_hitch_device_grants`, which creates one
new table; `20260824000001_enforce_hitch_device_grant_state`, which adds the
stored token-endpoint authentication method and state constraints; and
`20260824000002_add_operator_registration_provenance_to_hitch_clients`, which
records whether a confidential client was registered by the operator. The
second migration clears any device grants minted by a 0.4
prerelease because the earlier schema did not record enough information to
classify them safely; an agent mid-flow asks for a new code. Client
registrations, issued access tokens, and every existing 0.3 row are preserved.
Run all three migrations before serving 0.4 code. Client registration and
credential tasks read and write the provenance column even while device
authorization is disabled; `bin/rails hitch:doctor` reports missing schema.

## Step 3 — decide whether to enable it

The feature is off by default and stays off until you say otherwise:

```ruby
# config/initializers/hitch.rb
config.device_authorization_enabled = true
```

While off: `POST /oauth/device_authorization` and `/activate` answer 404,
the token endpoint refuses the grant with `unsupported_grant_type`, and
discovery advertises neither.

**Know who can use it.** A device grant requires a vouched client: a CIMD
client (Claude and other spec-following MCP clients), or a confidential
client you register at your console with
`hitch:clients:create_confidential`. Self-registered clients from
`/oauth/register` are refused even if DCR issued a secret — authentication is
not operator endorsement, and an unvouched device code is the RFC 8628 §5.4
phishing shape.

The old schema could not distinguish operator-created confidential clients
from confidential DCR clients, so every existing row starts unvouched for this
new flow. Browser authorization and token exchange keep working. To let an
existing confidential client use device authorization, rotate its secret and
restate the name you want shown on the approval screen:

```bash
bin/rails hitch:clients:rotate_secret CLIENT_ID=nightly-reporter \
  NAME="Nightly Reporter" OUTPUT_FILE=nightly-reporter.credentials
```

**Before enabling in production, check your cache store.** Both device
quotas — per-IP minting and per-principal code verification — fail closed,
because the short user code's safety is arithmetic over the rate limit. A
store that cannot count across processes (`:memory_store`, `:null_store`,
`:file_store`) refuses the boot when the flag is on. A shared
`config.cache_store` (Solid Cache, Redis, Memcached) satisfies it, or set
`config.device_authorization_rate_store` explicitly.

## Step 4 — add the cleanup call

If you scheduled a cleanup job per the README, add the second line:

```ruby
class CleanupMCPTokensJob < ApplicationJob
  def perform
    Hitch::AccessToken.cleanup_expired!
    Hitch::DeviceGrant.cleanup_expired!
  end
end
```

The issued tokens carry the audit trail, so this deletes rows a day past
expiry — the day keeps the `expired_token` / `access_denied` answer a
slow-polling device hears honest regardless of job timing. Budget roughly a
day's worth of mint volume in `hitch_device_grants`; without the job (and
with the flag on), expired grants accumulate at your mint rate.

## Step 5 — verify

```bash
bin/rails hitch:doctor      # expect migrations: current
```

With the flag on, confirm discovery advertises the grant:

```bash
curl -s https://your-app.example.com/.well-known/oauth-authorization-server \
  | grep -o '"device_authorization_endpoint":"[^"]*"'
```

Then run the flow end to end once, as a person: POST the endpoint with a
registered client_id, open the `verification_uri_complete` link on your
phone, and check the /activate page renders inside your app's layout with
your sign-in in front of it. Hitch's own
`test/integration/device_authorization_flow_test.rb` is the model if you
want an automated version.

## What might break in your app

With the flag left off: only tests that snapshot discovery metadata or
`hitch:doctor` output (one new table in `migrations`). With it on:

1. **A host route named `/activate`.** The engine is mounted at your root,
   and your route declared before the mount silently wins — the device flow
   then breaks invisibly. Rename one of them.
2. **Snapshot tests over discovery metadata.** `grant_types_supported` gains
   `urn:ietf:params:oauth:grant-type:device_code` and
   `device_authorization_endpoint` appears.

## The screen's words are load-bearing

`/activate` ships with warning copy — "Only enter a code you asked a device
for" — required in spirit by RFC 8628 §5.4: the flow's known abuse is a
stranger sending someone a code to approve. If you override
`app/views/hitch/activations/*.html.erb` to match your product's voice, keep
that meaning intact. The page also displays only a voucher's word — a
metadata client's document host, or an operator-registered client's
console-chosen name — never a self-declared name or a self-asserted
redirect host. Preserve that too.

## Rolling back

```bash
bin/rails db:migrate:down VERSION=20260824000002
bin/rails db:migrate:down VERSION=20260824000001
bin/rails db:migrate:down VERSION=20260824000000
```

Then restore the 0.3 constraint in your `Gemfile` and `bundle install`.
Pending device grants disappear — an agent mid-flow starts over. Tokens
already issued through the flow are ordinary access tokens and keep working;
nothing an adopter owns is lost.
