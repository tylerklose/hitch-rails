# Work packet: M8

## Scope

Stabilize one immutable `0.2.0` artifact and one honest public contract. Reconcile
API/migration/security/release docs and evidence index; run full CI/matrix/
conformance/package/client/mutation/adoption gates; retain visible capability
skips and two documented untestable probes; obtain explicit authority for the
exact final candidate; then publish, download, and verify RubyGems bytes.

## Not in scope

- Hiding skips/failures/baselines, rewriting published tags/gems, silently
  dropping supported lanes, or adding last-minute public API without repeating
  its owning milestones.
- Publishing without maintainer and Tyler-owned adoption approvals.

## Target files/API

- final changelog/API/security/upgrade/removal/release docs, `CONTRIBUTING.md`,
  reviewed evidence templates, and the evidence index.
- replace the pre.4-frozen `SECURITY.md` "internal checkpoint verification
  matrix" wording with the exact two-profile pre.4 and four-lane final evidence
  boundary in the source-bound final candidate; do not mutate the accepted
  pre.4 bytes to make that correction early.
- `docs/contracts/release_evidence.yml`, the complete evidence index,
  prepublication readiness gate, and postpublication downloaded-gem verifier.
- `docs/contracts/release_matrix.yml`, four exact locked appraisal pairs, hosted
  Ruby rows, and `bin/verify-release-matrix`.
- `docs/evidence_templates/0.2.0/` and
  `bin/validate-release-evidence-draft`, which validate authoring shape and
  reject unresolved placeholders without claiming semantic acceptance.
- `bin/final-local-gates`, which rebuilds the clean final source and writes one
  exclusive, candidate-bound digest report for the fixed local gate set.
- all public constants/configuration/generators/events/task output already
  frozen in the manifest; everything else remains private.

The released gem/tag/docs/checksums must identify the same bytes, source tree,
and contract. Readiness, publication authority, and downloaded-byte
reconciliation are three separate states.

## Dependencies

M7/`0.2.0.rc2` and both adoption approvals are accepted. No unresolved blocker,
dual route, stale baseline, hidden database/client requirement, or unowned
security control remains.

## Acceptance commands

First materialize the clean source-bound `0.2.0` candidate outside the
repository:

```sh
mkdir -p /tmp/hitch-0.2.0-product-candidate
bin/prepare-release-artifact --candidate 0.2.0 /tmp/hitch-0.2.0-product-candidate
```

Obtain Tyler's explicit approval, then run both pinned product clients against
a disposable loopback host using those exact staged gem bytes. Record each
run's start and completion times, candidate SHA, complete OAuth/MCP checks, and
sanitized report digest; accept `product-smokes.json` only after both runs
finish. Product runs remain forbidden before approval.

Only after accepting that product evidence, run the matrix contract and
generate the fixed local-gate report outside the repository:

```sh
bin/verify-release-matrix
HITCH_FINAL_LOCAL_GATES_REPORT=/tmp/hitch-0.2.0-local-gates.json bin/final-local-gates
```

The generated report runs `bin/ci`, both named `bin/conformance-auth` profiles,
`bin/conformance-server`, `bin/package-apps`, `bin/client-smokes --automated`,
`bin/mutation-mcp`, and `bin/contract`; it retains output digests plus the
candidate-bound structured package/client report digests, forces test mode,
clears generic database authority, and refuses HEAD/tree drift. Review the
hosted GitHub Actions push run and create `hosted-matrix.json` with its canonical
repository, candidate head SHA, event, run/attempt, candidate workflow SHA, and
four distinct contracted job outcomes. The hosted run and every local gate must
start after the product-client record's acceptance timestamp. A pull-request
run does not qualify because its default checkout is a synthetic merge commit.
No unexplained skip,
unexpected failure, or stale baseline entry is permitted. Accept `product-smokes.json`,
`hosted-matrix.json`, and the generated `final-local-gates.json`, then create
`final-check.json`. The latter binds all historical records, both adoptions,
product evidence, hosted matrix evidence, and every local gate to the generated
bundle; it rebuilds the final gem from its exact source commit/tree and
SHA-256. RC2-to-final runtime or public-API drift is forbidden: change RC2 and
repeat both adoptions instead; the version-file exception permits only the
exact RC2-to-final version literal with every other byte unchanged. A named
release maintainer reviews only after every bound prerequisite's authoritative
`verified_at`, `recorded_at`, or `verified_on` completion value and records that
identity, role, and approval time before final verification. Each prerequisite
kind owns one exact completion field; a different field may
not substitute for a missing or malformed value. The canonical work-packet
graph is deterministically generated, so its completion authority is the bound
`work_packet_verification.verified_on` record only when that companion's graph
path and SHA-256 match the accepted graph record.

Before indexing a hand-authored record, run the matching template validator in
ready mode; this checks shape and rejects placeholders, while the main verifier
remains the semantic authority:

```sh
bin/validate-release-evidence-draft --ready hosted_matrix /tmp/hosted-matrix.json
```

Validate that candidate while publication authority remains pending.
This gate prints the
exact source, artifact, and final-check digests for the authority reviewer and
fails if authority was already recorded:

```sh
bin/verify-release-evidence --ready-for-authority 0.2.0
mkdir -p /tmp/hitch-0.2.0-authority-review
bin/prepare-release-artifact --ready-for-authority 0.2.0 /tmp/hitch-0.2.0-authority-review
```

A named release authority, Tyler Klose, then reviews that exact candidate and
final-check digest and creates `final-publication-authority.json`. After accepting that
record in the index, run the public preflight:

```sh
bin/verify-release-evidence --preflight 0.2.0
bin/release-check --validate-version 0.2.0
mkdir -p /tmp/hitch-0.2.0-authorized
bin/prepare-release-artifact 0.2.0 /tmp/hitch-0.2.0-authorized
```

Only then may the maintainer create annotated tag `v0.2.0`, targeting the
authorized source commit/tree, and publish only the staged authorized gem bytes.
The staging command requires an existing external directory, refuses repository
paths, and refuses an existing artifact path. Capture
the read-only downloaded-byte report outside the repository:

```sh
HITCH_RELEASE_REPORT=/tmp/hitch-0.2.0-downloaded.json bin/release-check 0.2.0
```

Review and commit that report as the downloaded-gem evidence, change its index
entry from `pending` to `accepted` with the exact SHA-256, and run:

```sh
bin/release-check --complete 0.2.0
```

The live check requires the exact annotated tag object and peeled commit on the
canonical GitHub repository; a local-only tag cannot satisfy completion.
