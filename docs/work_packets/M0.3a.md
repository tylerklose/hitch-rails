# Work packet: M0.3a

## Scope

Make redirect registration portable across SQLite and PostgreSQL while
preserving a safe upgrade path for the unreleased PostgreSQL-array schema.
Fresh installs create `hitch_client_redirect_uris` with a foreign key and unique
`(hitch_client_id, uri)` index, create `hitch_schema_states(key, version)`, and
seed `redirect_uris=2`; they never create an array column.

An additive upgrade migration must recognize the legacy array column, create
the normalized/state tables, backfill distinct valid stored strings, and seed
`redirect_uris=1` without dropping legacy data. While state is 1,
`Hitch::Client` reads legacy values and writes both representations in one
transaction. `redirect_uris=` replaces both sets, and every path including
`register!` and confidential registration uses that writer. State reads come
from the primary database on every redirect operation and are not process
cached. Missing, duplicate, or non-1/2 state is corruption and fails closed;
never infer state 2. Normalized reads return URI-sorted values, and deleting a
client cascades to its redirect rows at the database level.

## Not in scope

- The state-1-to-state-2 cutover, rollback preparation task, or final
  reconciliation; M0.3b owns them.
- Authorization-code compare-and-swap; M0.3b owns it.
- Dropping the legacy column or state row; neither is removed before 1.0.
- Claiming safe mixed-version rolling writes.

## Target files/API

- `db/migrate/20260528020918_create_hitch_tables.rb`: change only the fresh
  client schema to normalized redirects plus schema state version 2.
- `db/migrate/*_normalize_hitch_client_redirect_uris.rb` (new): additive,
  adapter-aware legacy upgrade to normalized rows and state version 1. It must
  handle duplicate legacy values deterministically and leave the array intact.
- `app/models/hitch/client_redirect_uri.rb` (new): table mapping and client
  association with database-backed uniqueness and an `ON DELETE CASCADE`
  foreign key.
- `app/models/hitch/schema_state.rb` (new): private primary-database lookup for
  the `redirect_uris` authority version; no application cache.
- `app/models/hitch/client.rb`: normalized association, state-aware reader, and
  explicit transactional replacement writer used by every registration path;
  do not persist redirect domain behavior from an `after_save` callback.
- `test/hitch/client_redirect_uri_test.rb` and
  `test/integration/redirect_storage_migration_test.rb` (new): fresh and legacy
  fixtures under both adapters, including duplicates, empty arrays, rollback,
  retry, and write parity.
- `gemfiles/rails_7_2_sqlite.gemfile` and
  `gemfiles/rails_8_1_postgresql.gemfile`: change only if resolution proves an
  H0 bound unusable; record any bound change in evidence.

`Hitch::Client#redirect_uris`, `redirect_uris=`, `register!`, and
`register_confidential!` retain their public shapes. Redirect-row and schema-
state classes are internal persistence mechanism and are excluded from the
public API manifest.

## Acceptance commands

Run the H0 boot smokes, then the issue-owned migration/model tests in both
profiles:

```sh
bin/ci-appraisal rails_7_2_sqlite
bin/ci-appraisal rails_8_1_postgresql
bin/ci-appraisal rails_7_2_sqlite -- \
  bin/rails test test/hitch/client_redirect_uri_test.rb \
  test/integration/redirect_storage_migration_test.rb
bin/ci-appraisal rails_8_1_postgresql -- \
  bin/rails test test/hitch/client_redirect_uri_test.rb \
  test/integration/redirect_storage_migration_test.rb
```

The tests own their file-backed temporary databases and separate connections;
they must not rely on the repository dummy database or mutate `db/schema.rb`.
Also run `bin/rubocop` and `RAILS_ENV=test bundle exec rake
app:zeitwerk:check`.

## Evidence paths

Create `docs/evidence/0.1.0/migrations/redirect-storage.json`. Record each
appraisal's resolved Ruby/Rails/adapter versions, fresh/upgrade fixture counts,
duplicate cleanup counts, state value, dual-write parity, rollback/retry result,
commands, and exit statuses. Store no redirect URIs from non-fixture data.

## Rollback

R2: keep the additive normalized and state tables and preserve legacy writes.
Before any state-2 cutover, reverting application code restores legacy reads.
Do not reverse the upgrade migration in an adopted database merely to roll back
code; empty disposable databases may reverse normally.

## Estimate

Four engineering days. Risk is high because this changes fresh schema,
upgrade behavior, association semantics, and cross-adapter compatibility.

## Risks

- Editing the fresh migration and adding an upgrade migration can double-create
  tables unless each path detects its starting schema explicitly.
- Association callbacks can create partial dual writes; replacement must be one
  transaction with database uniqueness as the final invariant.
- A cached state value makes cutover process-dependent and breaks rollback.
- SQLite acceptance can look green while still exercising PostgreSQL through an
  ambient `DATABASE_URL`; the appraisal's adapter assertion must remain active.

## Owner

The Hitch release maintainer is accountable. A contributor may implement the
packet, but the release maintainer accepts migration, rollback, and cross-
adapter evidence before M0.3b starts.
