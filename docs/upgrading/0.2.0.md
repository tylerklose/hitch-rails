# Upgrading to Hitch 0.2

These steps are for an installation moving from the auth-only 0.1 line or a
host-owned MCP endpoint to 0.2.

## Before changing the canonical route

1. Back up every `hitch_*` table and record the deployed application and Hitch
   commits.
2. Complete the [0.1 adoption and redirect cutover](0.1.0.md). Version 2 must
   be the normalized redirect authority before the final 0.2 route switch.
3. Inventory the old MCP controller, tool names and schemas, OAuth scopes,
   argument policy, audit meaning, and clients. A framework migration must not
   silently broaden any of them.
4. Confirm production `config.cache_store` can count across processes — Solid
   Cache, Redis, or Memcached. Nothing new to provision if you already cache.
   Follow the [request admission guide](../operator/rate_limiting.md).

## Install the host-owned runtime

```sh
bin/rails generate hitch:install
bin/rails db:migrate
bin/rails generate hitch:tool echo --deny-default
```

Both generators refuse collisions before writing. If an existing canonical
controller or `/mcp` route collides, keep it in place while preparing a
namespaced controller or an isolated preview; do not overwrite it. The
installer supports `--controller-name Admin::McpController`.

If you carried a pre-release configuration that set `config.mcp.*` knobs
across two initializers, fold them into `config/initializers/hitch.rb` and
add `config.mcp.enabled = true` — without the switch the app boots green
with the MCP runtime off, and `bin/rails hitch:doctor` reports it disabled.

For a migration from a host-owned endpoint, `--deny-default` generates the
hardened variant — hidden, denying, and unimplemented — so nothing becomes
callable before you port the old tool's schema, availability, argument
authorization, and Result return onto it deliberately. (Without the flag,
`hitch:tool` generates a working registered tool.)

## Verify before cutover

In an isolated environment, verify OAuth discovery and token exchange, then
use `Hitch::MCP::TestHelper` to discover, list, and call with real host policy.
Run:

```sh
bin/rails hitch:doctor
HITCH_DOCTOR_FORMAT=json bin/rails hitch:doctor
```

Every doctor failure blocks cutover. Review warnings: an empty Registry means
no tool is exposed; the memory store is supported only outside production; a
noncanonical deprecated endpoint is acceptable only during a staged migration.

Replace the canonical route atomically only after the preview proves the same
or narrower tool visibility, scopes, and argument behavior. Keep the old route
change revertible until exact client smokes pass.

## Rollback

Route rollback is a host deployment operation. Restore the previous canonical
route first if the new endpoint is unhealthy. While the gem remains installed,
`bin/rails destroy hitch:tool ...` removes each generated tool and its
registration line, and `bin/rails destroy hitch:install` reverses the
install; your version control history covers anything you customized on top.

Do not drop Hitch tables as part of application rollback. Follow the
[removal guide](../removing.md) for long-term data retention and uninstall
decisions.
