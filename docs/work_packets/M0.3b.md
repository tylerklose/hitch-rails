# Work packet: M0.3b

## Scope

Finish the redirect cutover protocol and replace PostgreSQL row-lock syntax
with adapter-neutral, exactly-once authorization-code consumption. Add
`hitch:redirects:cutover` to drain/reconcile state 1 and atomically move it to 2,
and `hitch:redirects:prepare_rollback` to prove representation parity and move
state 2 back to 1 before old writers return. Both tasks are idempotent, use the
primary database, and fail without changing state when parity checks fail.

Code exchange must use a compare-and-swap whose predicates include a pending,
unexpired code after client, resource, confidential authentication, and PKCE
have passed. Exactly one concurrent update may install the token digest and
clear code fields. The winner returns the one raw token it generated; losers
receive `invalid_grant`. On SQLite, do not wrap a read-plus-write sequence in a
deferred transaction: execute the final conditional update atomically so the
loser observes zero affected rows instead of a lock-upgrade failure. Exercise
separate connections and real concurrency on file-backed SQLite and PostgreSQL.

## Not in scope

- Mixed-version rolling writes; operators must drain redirect-mutating old
  writers before either state transition.
- Removing the legacy redirect column/state row before 1.0.
- Changing public registration or token response shapes.
- Distributed locks, queues, or retry frameworks.

## Target files/API

- `app/models/hitch/schema_state.rb`: transactional state transition helpers
  with primary reads and row/update serialization supported by both adapters;
  transaction blocks return ordinary values and never use method-level `return`.
- `app/models/hitch/client.rb`: final idempotent backfill/parity operations used
  by cutover and rollback preparation; normal state-2 reads use normalized rows
  while continuing legacy writes for code rollback.
- `app/models/hitch/access_token.rb`: adapter-neutral
  `exchange_authorization_code!` boundary or equivalent single model operation
  that owns PKCE validation and the conditional state transition.
- `app/controllers/hitch/tokens_controller.rb`: call the model exchange boundary
  and remove `FOR UPDATE SKIP LOCKED` and controller-owned transaction logic.
- `lib/tasks/hitch.rake`: add both redirect transition tasks with explicit
  drain/traffic warnings and nonzero failure exits.
- `bin/ci-migrations` (new in this issue): run fresh/upgrade/cutover/rollback and
  concurrent-exchange suites through both H0 appraisal profiles.
- `test/integration/redirect_cutover_test.rb` and
  `test/integration/concurrent_code_exchange_test.rb` (new), plus focused access
  token tests for failed-check retry and exactly-once exchange.

The rake tasks are public operator API and enter the M0.5 manifest. Model
transition/CAS helpers remain private implementation unless the manifest
explicitly says otherwise.

## Acceptance commands

Run:

```sh
bin/ci-migrations
bin/ci-test test/hitch/access_token_test.rb \
  test/integration/oauth_flow_test.rb \
  test/integration/confidential_client_test.rb \
  test/integration/redirect_cutover_test.rb \
  test/integration/concurrent_code_exchange_test.rb
bin/rubocop
```

`bin/ci-migrations` must invoke both H0 appraisal profiles and fail unless fresh
install, legacy backfill, duplicate cleanup, state-1 dual write, cutover,
state-2 read/legacy write, rollback preparation, and forward re-cutover pass.
Concurrency tests use at least two independent connections and prove one token
for one code under both adapters. Mutation checks must fail if the CAS predicate,
client/resource/PKCE prerequisite, or parity check is removed.

## Evidence paths

Create:

- `docs/evidence/0.1.0/migrations/redirect-cutover.json` for state transitions,
  row counts, parity, and rollback rehearsal; and
- `docs/evidence/0.1.0/auth/concurrent-exchange.json` for adapter, connection,

Use synthetic identifiers and hashes only. Raw database/log output remains a CI
artifact.

## Rollback

R2: drain redirect-mutating traffic and run
`bin/rails hitch:redirects:prepare_rollback` while new code is active; deploy old
code only after state 1 commits. If preparation cannot run, keep redirect
mutation disabled until new code is restored and reconciles the database.
CAS code itself is R1 after dependent changes are drained; additive schema stays.

## Estimate

Three engineering days. Risk is high because this owns live upgrade authority,
rollback ordering, and one-time credential issuance under concurrency.

## Risks

- A task that flips state before checking every row can make a partial backfill
  authoritative.
- Test transactions can hide real independent-connection races.
- Generating a second raw token after a successful database transition loses
  correspondence with the stored digest.
- Retrying ambiguous database failures must inspect state rather than issue a
  second token.
