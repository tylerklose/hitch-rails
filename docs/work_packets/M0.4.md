# Work packet: M0.4

## Scope

Make the auth-only HTTP surface default-deny and reconcile every current public
claim with checkpoint behavior. Replace hard-coded origins with exact
`allowed_origins` configuration and validate preflight origin, requested method,
and requested headers before returning 204. Development/test may allow explicit
loopback origins; production does not infer them. Validate request Host against
the canonical resource host plus explicit `allowed_hosts` before deriving
issuer/discovery URLs.

Add `dynamic_client_registration_enabled` and an unauthenticated per-IP fixed-
window DCR limit. The library fallback keeps DCR enabled for an existing
unreleased installation and emits one actionable warning; the generated
initializer sets it false for new installs. Disabled DCR is omitted from
metadata and returns a stable not-found response. Production DCR requires a
host cache store whose single `increment`
operation counts the key, establishes first-write expiry, and
returns the post-increment integer. Missing, incapable, non-shared, malformed,
or failing stores fail closed. Development/test may use any cache store,
counting or not; the auth-only gem adds no cache/Redis dependency.

Remove configuration values with no production reader. Audit README, SECURITY,
CHANGELOG, initializer comments, code comments, warnings, and tests for stale
consent paths, RFC 9207 `iss`, database support, SDK ownership/version, CORS/DCR
defaults, and the `/mcp` boundary.

## Not in scope

- MCP endpoint CORS/rate limiting introduced in 0.2; this packet covers the
  auth/discovery/DCR surface verified at the internal 0.1 checkpoint.
- Redis as the 0.2 endpoint dependency.
- A fleet-global DCR quota or distributed lease.
- New OAuth grant types, client authentication methods, or browser UI.
- Public distribution; M0.5 owns internal gem packaging and matrix automation.

## Target files/API

- `lib/hitch/configuration.rb`: add and validate `allowed_hosts`,
  `allowed_origins`, `dynamic_client_registration_enabled`,
  `dynamic_client_registration_limit`, and
  `dynamic_client_registration_rate_store`.
- `lib/generators/hitch/install/templates/initializer.rb`: generate explicit
  default-deny origins/hosts and disabled DCR with operational comments.
- `app/controllers/concerns/hitch/cors_support.rb`: remove vendor constants;
  implement exact configured origin and preflight validation.
- `app/controllers/hitch/public_endpoint_controller.rb` and
  `app/controllers/concerns/hitch/issuer_url.rb`: reject invalid Host before URL
  derivation or credentials.
- `app/controllers/hitch/registrations_controller.rb`: enforce DCR mode and the
  per-IP limit before parsing/registration.
- `lib/hitch/dynamic_registration_rate_limit.rb` (new): private fixed-window
  orchestration keyed by a one-way digest of normalized `request.remote_ip`,
  strict shared-store capability/return checks, and a bounded non-production
  memory fallback.
- `app/controllers/hitch/metadata_controller.rb`: advertise DCR only when
  enabled while preserving CIMD truthfulness and private Host-varying metadata.
- `config/routes.rb`: keep OPTIONS routes mapped only to actions that exist and
  ensure disabled DCR does not create a second behavior path.
- `lib/hitch/engine.rb`: boot validation and one-time upgrade warnings.
- `README.md`, `SECURITY.md`, `CHANGELOG.md`, `lib/hitch.rb`, gemspec prose, and
  affected source/test comments: align documentation with the 0.1 contract.
- `bin/ci-http` and `bin/prose-audit` (new in this issue): run the HTTP boundary
  suite and fail on the enumerated stale phrases/paths.
- `test/integration/cors_and_host_test.rb` and
  `test/integration/dynamic_registration_posture_test.rb` (new), plus existing
  metadata, OAuth, generator, and CSRF tests.

The five configuration readers above are public 0.1 API and must be described in
M0.5's manifest. HTTP helpers and limiter keys remain private.

## Acceptance commands

Run:

```sh
bin/ci-http
bin/prose-audit
bin/ci-test test/integration/cors_and_host_test.rb \
  test/integration/dynamic_registration_posture_test.rb \
  test/integration/oauth_flow_test.rb \
  test/hitch/install_generator_test.rb
bin/rubocop
RAILS_ENV=test bundle exec rake app:zeitwerk:check
```

The HTTP suite must prove allowed OPTIONS returns 204 with only configured
headers; missing/disallowed origins and disallowed methods/headers do not gain
  CORS; invalid Host is rejected before discovery or OAuth work; disabled DCR is
  not advertised and cannot register; enabled DCR is IP-limited per process;
  shared-store capability/return/operation failures close registration before
  model work; and loopback exceptions never activate in production.
`bin/prose-audit` must enumerate its searched old phrases and fail when any
remain outside an explicit historical fixture.

## Evidence paths

Create `docs/evidence/0.1.0/http/posture.json` with the config profile, named
request vectors, statuses/headers, zero-work assertions, commands, and versions.
Create `docs/evidence/0.1.0/prose-audit.json` with searched files/patterns,
allowlisted historical fixtures, and a zero-stale-match result. Do not record
Authorization headers, bodies, tokens, secrets, or raw exception text.

## Rollback

R1: revert behavior, tests, and prose together before checkpoint acceptance. If an
operator enabled DCR under the new configuration, do not silently restore an
unbounded endpoint; forward-patch or keep DCR disabled while reverting unrelated
changes.

## Estimate

Three engineering days. Risk is medium: the behavior is bounded, but Host/CORS
and unauthenticated registration are public security boundaries and prose drift
can misconfigure adopters.

## Risks

- Reflecting Origin before an allowlist decision creates credentialed cross-
  origin access.
- Rails routing can return an unrelated 404/500 instead of the documented
  preflight outcome unless the real route/action is tested.
- Deriving issuer metadata from an unvalidated Host enables discovery poisoning.
- Existing-install compatibility can accidentally override a new installer's
  explicit DCR disablement; test both configuration cohorts.
- A store can claim the interface while implementing increment and expiry as
  separate operations; production documentation must make atomicity part of
  the operator-owned contract and integration tests must exercise the one-call
  boundary.
